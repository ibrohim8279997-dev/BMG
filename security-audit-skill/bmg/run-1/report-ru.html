Сценарий атаки. Одобренный продавец может отметить доставленным любой оплаченный заказ со своими позициями — без подтверждения клиента и доказательств. 4. Подмена X-Forwarded-For обходит все IP-ограничения

Высокийподтверждено по коду, нужна проверка запуском · xff-spoofing-via-next-proxy

Где:

  • apps/core/utils.py:4-12 (client_ip берёт parts[-NUM_PROXIES])
  • config/settings.py:96; backend/.env.example рекомендует NUM_PROXIES=1
  • frontend/node_modules/next/dist/server/base-server.js:567 (x-forwarded-for ??= remoteAddress — заголовок клиента сохраняется)

Сценарий атаки. Next 15 не дописывает адрес к XFF, а оставляет значение клиента. При NUM_PROXIES=1 Django берёт последний элемент — его выбирает атакующий. Обходятся: IP-allowlist админки (core/permissions.py:19-25; остаются пароль + TOTP), CLICK_ALLOWED_IPS (подпись Click всё ещё защищает), CRM_READ_ALLOWED_IPS, все лимиты по IP (вход, коды, регистрация аккаунтов на IP). Смена XFF на каждый запрос даёт неограниченные «корзины» лимитов. При NUM_PROXIES=0 (дефолт кода) наоборот все пользователи делят один IP прокси — один атакующий исчерпывает лимит входа для всех.

Исправление. Поставить перед Next доверенный edge (nginx), который перезаписывает заголовок: proxy_set_header X-Forwarded-For $remote_addr; либо в Next выставлять XFF из адреса сокета. Затем задать точный NUM_PROXIES, исправить комментарий в .env.example, слушать Django только на 127.0.0.1.

19. Админ-вход: DoS блокировкой и слабые места 2FA

Низкийподтверждено по коду · admin-auth-hardening

Где:

  • apps/adminpanel/views.py:36-45,57-59,66-75,86-87
